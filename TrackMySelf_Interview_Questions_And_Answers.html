Question 1 Project Overview
Tell me about your project.
I built TrackMySelf, a production-grade, offline-first personal management and wellness mobile application developed using Flutter, Dart, and Drift ORM (SQLite v3).

The application consolidates four fragmented aspects of daily personal life into a single cohesive, high-performance experience:
  • Health & Fitness: Calorie tracking, macro breakdown, Mifflin-St Jeor metabolic calculations (BMR/TDEE), and visual body transformation progress galleries with weight delta tracking.
  • Daily Routines & Habits: Habit tracking with an automated contiguous streak calculation engine, time-of-day filtering, and scheduled local notifications.
  • Time & Agendas: An interactive monthly calendar with category-coded multi-event dot indicators and scheduled agenda reminders.
  • Memory & Asset Tracker: A purchase and warranty management tool with camera/gallery receipt capture and automated 7-day pre-expiry alerts.
The application follows Clean Architecture with Provider state management, is validated by 52 automated unit, domain, and DAO tests (100% pass rate), has 0 static analysis warnings, and compiles to an optimized 64 MB release APK.
Question 2 Problem Statement & Value
What problem does your project solve?
Most users currently need 4 to 5 separate apps—one for calorie tracking (like MyFitnessPal), one for habits (like Habitica), one for calendar events, and another to keep track of purchase receipts and warranties. This creates app fatigue, high recurring subscription costs, and major privacy concerns because sensitive health and financial data are stored on third-party cloud servers.

TrackMySelf solves this by:
  • Consolidating Workflows: Unifying fitness, habit building, agenda management, and asset tracking into a single executive dashboard with real-time vitals and summary tiles.
  • 100% Data Privacy & Offline Guarantee: Storing all relational data, photos, and calculations entirely on the device using an embedded SQLite database, requiring zero internet connection and zero cloud subscriptions.
  • Zero Latency: Immediate response times with no network loading spinners or offline sync conflicts.

Question 6 Technology Stack & Decisions
What technologies did you use and why?
  • Flutter & Dart 3.x: Cross-platform single codebase with native 60–120 FPS performance and strong compile-time type safety.

Question 7 System Architecture
Explain the architecture of your project.
The project follows Clean Architecture with a Feature-First structure.

Inside lib/, code is divided into core/ (shared database, themes, notification services, shared widgets) and feature modules (auth/, fitness/, habits/, calendar/, purchases/, home/).

Each feature is organized into three distinct layers:
  1. Data Layer: Contains DAOs (Data Access Objects) and database tables that communicate with Drift SQLite.
  2. Domain Layer: Contains pure Dart entities, calculators (e.g., BMR, streaks, warranty state), and business rules with zero Flutter UI dependencies.
  3. Presentation Layer: Contains UI screens, reusable widgets, and ChangeNotifier providers that bind the domain to the view.
This strict separation allowed me to test all business logic in isolation using in-memory databases.
Question 8 Application Flow
Explain the complete flow of your application.
  1. App Launch & Auth Guard: main.dart initializes timezones, spins up the Drift database singleton, and loads the active user session. If no session exists, GoRouter redirects to the Login/Registration screen.
  2. Onboarding & Profile Setup: A new user inputs age, gender, height, weight, and activity level. The system calculates and persists their baseline BMR and TDEE.
  3. Executive Dashboard (Home): The user sees a scenic sunrise mountain header, daily motivational quote, real-time vitals strip, and a 4-tile health card summarizing calories consumed vs. burned, active habits, and today's schedule.
  4. Daily Logging & Interaction:
    • In Fitness, the user logs meals and workouts; progress rings update dynamically. Users can snap transformation progress photos and view weight deltas.
    • In Habits, checking off a habit triggers haptic feedback, increments the streak counter, and updates the daily completion banner.
    • In Calendar, the user schedules events with optional notification alerts.
    • In Purchases, the user logs items, attaches receipt photos, and sets warranty periods.
Question 9 Technical Difficulty
What was the most difficult part of the project?
The most complex part was retrofitting multi-user data isolation across legacy tables via Drift schema migrations (v1 to v3) without corrupting existing records.

Initially, the schema was single-user. When introducing authentication, every table required a non-nullable userId foreign key. I had to write a custom MigrationStrategy.onUpgrade script that inspected schema versions, created the Users table, added the new foreign key column with fallback defaults to preserve legacy data, and ensured that every DAO query strictly filtered by currentUserId to prevent cross-account data leaks.
Question 10 Engineering Challenges
What challenges did you face?
  1. Habit Streak Midnight Reset Bug: Streaks were resetting to 0 if checked early in the morning before completing a habit for that day.
  2. Android 12+ / 14 Exact Alarm Restrictions: Background reminders failed on newer Android versions due to strict battery optimization policies and uninitialized time zones.
  3. Image Cache & Disk Leaks: Receipt and transformation photos were disappearing after OS cache cleanups, or lingering orphaned when records were deleted.
  4. UI Layout Constraints: Images in the header and quote banners were either being clipped at the edges or distorted across different phone screen aspect ratios.
Question 11 Problem Solving
How did you solve those challenges?
  • For Streaks: I adjusted the streak anchor algorithm to accept either today OR yesterday as the valid contiguous starting date, providing a 1-day grace period.
  • For Notifications: I initialized the tz database via flutter_timezone, declared SCHEDULE_EXACT_ALARM and POST_NOTIFICATIONS in AndroidManifest.xml, and registered RECEIVE_BOOT_COMPLETED to reschedule alarms after a reboot.
  • For Images: I copied temporary camera files directly into getApplicationDocumentsDirectory() and implemented automatic File(path).delete() hooks when database records are deleted.
  • For UI Layout: I wrapped images in responsive containers using BoxFit.cover paired with Alignment.topCenter and uncropped card structures.

Question 16 Data Persistence
How did you store and retrieve data?
Data is persisted locally using Drift ORM with SQLite v3:
  • Structured Data: Stored across 7 relational tables with indexes on userId and timestamp columns.
  • Retrieval: For static screens, queries use .get(). For dynamic dashboards, queries use .watch(), which returns a reactive Dart Stream that automatically emits new data whenever an underlying table changes.
  • Binary Assets: Receipt and progress images are saved to the phone's sandboxed document directory, with their file paths stored as strings in SQLite.
Question 17 Application Security
How did you make your application secure?
  1. No Plaintext Passwords: User passwords are encrypted/hashed with standard SHA-256 before being saved to SQLite.
  2. Multi-User Isolation: Every query strictly enforces the authenticated userId, ensuring complete privacy on shared devices.
  3. Sandboxed File Storage: All photos are kept inside the app's private sandboxed directory, inaccessible to other third-party apps on the device without root access.
  4. No External Exposure: Because the app operates offline-first, personal data is never transmitted over insecure networks.
Question 18 Scalability & Cloud Architecture
How would you scale this application for 10,000 to 100,000 users?
Since the app is offline-first, client performance is already decentralized—each phone runs its own SQLite engine independently, so client CPU and database costs do not multiply with user growth.

To add cloud synchronization for 100,000+ users:
  1. Backend: Deploy a horizontally scalable REST or GraphQL API (Go, Node.js, or Supabase/PostgreSQL) behind an AWS Application Load Balancer.
  2. Sync Protocol: Implement an incremental change-data-capture (CDC) sync engine using updatedAt timestamps and soft deletes (isDeleted = true) to sync only modified rows.
  3. Media Storage: Offload receipt and body photos to Amazon S3 or Google Cloud Storage using pre-signed upload URLs and CDN caching (CloudFront).
  4. Caching & Queueing: Use Redis for auth token caching and rate limiting.
